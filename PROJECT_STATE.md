## Module Summary

### Backend

- `src/server.js` — Loads environment variables, connects to MongoDB, then starts Express on port 5000 by default. Used for local `npm run dev`/`npm start` only — not invoked on Vercel.
- `src/app.js` — Configures CORS and JSON parsing, mounts `/api` routes, and provides the health response at `/`. Exports the bare Express app (no `app.listen`), so it can be reused as-is by both `server.js` (local) and `api/index.js` (Vercel serverless).
- `api/index.js` — Vercel serverless function entry point; re-exports `src/app.js` unchanged. Added 2026-11-21 because Vercel's zero-config Node detection needs a handler under `api/` — deploying `vercel.json` alone with no `builds`/`api` folder left the backend with no function to route requests to, which is what was causing "Failed to fetch" in the deployed frontend regardless of CORS/env settings.
- `vercel.json` (backend) — `regions: ["bom1"]` plus a catch-all `rewrites` rule sending every path (`/`, `/api/*`) to `api/index.js`, since the Express app itself expects to see those original paths for its own routing/health-check logic.
- `src/config/db.js` — Opens the Mongoose connection using `MONGO_URI` and terminates startup on failure.
- `src/config/cloudinary.js` — Configures the Cloudinary SDK from `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` and exports the ready-to-use client.
- `src/constants/cities.js` — Static, curated list (~50) of Indian cities; the single source of truth for city validation (registration, profile updates) and the `/api/meta/cities` list the frontend's city dropdowns fetch. Standardizing on this exact list (rather than free-text city input) is what makes exact-match city filtering reliable.
- `src/constants/username.js` — Shared `USERNAME_REGEX` (3-30 chars: lowercase letters, numbers, periods, underscores) and an `isValidUsername` helper, used by both auth controllers' registration and profile-update validation.
- `src/utils/generateToken.js` — Creates JWTs containing the account ID and `user` or `business` role.
- `src/utils/postVisibility.js` — Shared `visibleNowFilter()` Mongo filter fragment (not expired, and — for offers with a `validFrom` — already started). Used by every feed/story/discovery query against `Post` so `expiresAt` and `validFrom` stay enforced consistently in one place instead of being duplicated per-query.
- `src/middleware/authMiddleware.js` — Verifies Bearer JWTs, loads the matching account, and enforces roles. If the token is valid but its account no longer exists (e.g. deleted after the token was issued), responds 401 directly rather than letting every downstream controller crash on a null `req.user`/`req.business`.
- `src/middleware/errorHandler.js` — Formats unhandled Express errors as JSON responses.
- `src/middleware/uploadMiddleware.js` — `multer` memory-storage config (image mimetypes only, 5MB limit) wrapped so file-type/size rejections return 400 instead of falling through to the generic 500 handler.
- `src/models/User.js` — Consumer account schema with name, a required unique `username` (lowercase, regex-validated against `constants/username.js`), email, password hash, interests, bio, avatar URL, and a required `city` (enum-validated against `constants/cities.js`) that scopes discovery and search to the account's local ecosystem.
- `src/models/Business.js` — Business account schema with business name, a required unique `username` (same validation as `User.js`), email, password hash, industry, description, logo URL, and a required `city` (enum-validated against `constants/cities.js`), same role as on `User.js`.
- `src/models/Post.js` — Business-owned categorized post schema with title, content, image URL + `imagePublicId` (Cloudinary asset id, needed to destroy the image on delete), tags, expiry (`expiresAt`, doubles as an offer's "valid until"), `validFrom` (offer-only), visibility, likes (`likes` for consumer likers, `businessLikes` for business likers — added 2026-11-03, see Change Log), and timestamps. Has a derived (not stored) `offerStatus` virtual (`upcoming`/`active`/`expired`) computed from `validFrom`/`expiresAt` vs. now, present only for `postType: 'offer'` — `upcoming` added 2026-11-03 so an offer's own derived status agrees with the `visibleNowFilter()` that now hides it from feeds/notifications before `validFrom`. Also has `status` (`active`/`deleted`) and `deletedAt` — deletion is a soft-delete lifecycle transition, not a hard remove; every read query across the app filters `status: 'active'`.
- `src/models/Collaboration.js` — Business-to-business collaboration schema with pending, active, completed, and rejected lifecycle states; legacy accepted records are normalized as active in responses. A partial unique index on `requestKey` prevents duplicate keyed pending requests while leaving legacy pending records readable.
- `src/models/Comment.js` — Comment on a post, authored by either a consumer or a business (2026-11-03: `user` and `business` refs are both optional but exactly one must be set, enforced by a `pre('validate')` hook — originally consumer-only, opened to businesses the same day; `content` trimmed/max 500 chars, timestamps), indexed by `{post, createdAt}`. Any logged-in account can create or read.
- `src/models/SavedPost.js` — Consumer bookmark of a post (`user`/`post` refs, timestamps), unique on `{user, post}` (same pattern as `Follow.js`), indexed by `{user, createdAt}` for the Saved page's newest-first listing.
- `src/models/Notification.js` — Consumer offer notification schema with read state and post reference; expiry is not duplicated here — it's read from the populated post's `expiresAt`.
- `src/models/Follow.js` — Unique consumer-to-business relationship with indexes for follower and following lookups.
- `src/models/Activity.js` — Append-only, timestamped consumer engagement log (`type`: `like`/`unlike`/`follow`/`unfollow`, plus optional `business`/`post` refs), indexed by `user`+`createdAt` and `business`+`createdAt`. Purely additive — records are written alongside the existing `Post.likes`/`Follow` writes, never replaces them — intended as the "recent activity" signal the future Explore page's ranking algorithm will read, since neither `Post.likes` (no per-like timestamp) nor `Follow` (a relationship record, overwritten/deleted on unfollow — not a history) can answer that on their own.
- `src/models/Connection.js` — Bidirectional business-to-business relationship (`requester`/`recipient`/`status` enum `pending|accepted|rejected`) with a canonical `pairKey` and partial unique index for open pairs. `openPair` and `viewerStatus` keep lookups/status role-aware and account for legacy records that do not yet have a key; collaboration acceptance upgrades or creates the matching connection.
- `src/controllers/userAuthController.js` — Registers (requiring a valid `city` and a unique, format-validated `username`), logs in by `email` **or** `username` (2026-11-20: `loginUser` now takes a single `identifier` field, lowercased/trimmed, matched against either field via `$or` — safe because both `email` and `username` already have `lowercase`/`trim` set on the schema), and returns/updates the profile (`/me`) of consumer accounts (name, username, bio, interests, avatarUrl, city). Username changes on update are re-validated and re-checked for uniqueness (excluding the account's own document) before being applied.
- `src/controllers/businessAuthController.js` — Registers (requiring a valid `city` and a unique, format-validated `username`), logs in by `email` **or** `username` (same `identifier`/`$or` pattern as `userAuthController.js`, added 2026-11-20), and returns/updates the profile (`/me`) of business accounts (businessName, username, industry, description, logoUrl, city). Same username validate-and-recheck-uniqueness behavior on update.
- `src/controllers/metaController.js` — Returns the static supported-cities list (`constants/cities.js`) for registration forms, profile editors, and the search city filter.
- `src/controllers/uploadController.js` — Streams an uploaded image buffer to Cloudinary (`localyze/posts` or `localyze/profiles` folder via `?type=`) and returns its hosted URL plus its `publicId` (needed later to destroy the asset).
- `src/controllers/businessController.js` — Returns a business's public profile (with follower/connection/collaboration counts, including `city` and `username`), plus its followers list, connections list, and visibility-aware posts-by-type list, for viewing any business's profile page (self or others). For a different business viewer, the profile also reports viewer-relative connection status and whether a collaboration request is pending. Also exposes `searchBusinesses` (`GET /api/businesses/search?q=&city=`) — regex name/industry match, exact-match city filter (defaults to the caller's own city when `city` is omitted); results include `username`.
- `src/controllers/postController.js` — Creates, reads, updates, deletes, and likes posts according to account role (offers require `validFrom`/`expiresAt` at creation); also serves a business's connections feed (real connections/follows are unfiltered by city; the same-industry backfill used when under-filled is scoped to the caller's own city), using `utils/postVisibility.js`'s `visibleNowFilter()` to exclude both expired and not-yet-started offers. Delete soft-deletes the post (`status: 'deleted'`, `deletedAt` recorded) and, if the post has an `imagePublicId`, destroys the Cloudinary asset (best-effort — a Cloudinary failure is logged but doesn't fail the delete response). `toggleLikePost` (2026-11-03: opened to businesses, previously consumer-only) toggles `likes` or `businessLikes` depending on `req.role` and returns their combined count; only writes an `Activity` document (`type: 'like'`/`'unlike'`) for a consumer actor — `Activity` is a consumer-only engagement log and has no field to record a business actor against, so a business like is intentionally not logged there (see Known Issues).
- `src/controllers/storyController.js` — Returns one latest eligible post per followed business for consumers or connected business for business accounts, using the shared `visibleNowFilter()`.
- `src/controllers/notificationController.js` — Lists consumer offer notifications, filtering out ones whose linked offer post has been deleted, has expired, or hasn't reached its `validFrom` start date yet (so a notification can't surface a not-yet-started offer that the feeds already hide), and marks them read.
- `src/controllers/commentController.js` — `getComments` (any logged-in account) lists a post's comments oldest-first, populating both `user` and `business` (only one is ever set per comment); `addComment` (any logged-in account, 2026-11-03: previously consumer-only) creates one after validating non-empty content and that the post exists/is active, setting `user` or `business` based on `req.role`.
- `src/controllers/savedPostController.js` — `savePost`/`unsavePost` (consumer-only) create/remove a `SavedPost` row for the logged-in consumer (409 on an already-saved post rather than a duplicate row); `getSavedPosts` lists the consumer's saved posts newest-first, populated with business info, silently dropping any whose underlying post was since deleted.
- `src/controllers/followController.js` — Creates, removes, checks, and lists consumer follows for businesses. `followBusiness`/`unfollowBusiness` each also record an `Activity` document (`type: 'follow'`/`'unfollow'`) on the success path only — not on the duplicate-follow (409) or not-found (404) paths, since no state actually changed there.
- `src/controllers/collaborationController.js` — Sends, lists, accepts/rejects, and completes business collaborations; activating one auto-creates (or upgrades) a Connection between the two businesses. Pending requests have a canonical request key so concurrent repeated sends return the same pending request rather than creating duplicates.
- `src/controllers/connectionController.js` — Sends connection requests, checks status relative to the caller, lists received pending requests, accepts/rejects, and disconnects an existing accepted connection. Duplicate responses include the caller-relative status, and pair lookups support legacy rows without a canonical key.
- `src/controllers/discoverController.js` — `discoverPosts` (consumer Home feed) returns only posts from businesses the consumer follows (via `Follow`), newest first, with no interest/city backfill — an empty follow list returns `[]` by product decision; that fallback is what `discoverExplore` now provides on its own page instead. `discoverExplore` (new 2026-11-03, the Explore page's backend — `GET /api/discover/explore`) returns posts from businesses matching the consumer's `city` or `interests`, regardless of follow status, newest first, paginated; returns `[]` immediately if the consumer has neither a city nor interests to match on, otherwise resolves the matching business ids first, then queries `Post` scoped to them (active, visibility-appropriate, `visibleNowFilter()`). `discoverBusinesses` is unchanged: interest-matched businesses scoped to the consumer's own `city`, each flagged with the caller's current follow status.
- `src/routes/index.js` — Mounts authentication, posts, collaboration, connection, business-profile, upload, discovery, saved-posts, and meta route groups.
- `src/routes/userAuthRoutes.js` — Consumer register/login/get-me/update-me route definitions.
- `src/routes/businessAuthRoutes.js` — Business register/login/get-me/update-me route definitions.
- `src/routes/uploadRoutes.js` — `POST /image` (any logged-in account) — parses a multipart image upload and returns its Cloudinary URL.
- `src/routes/metaRoutes.js` — Public `GET /cities` route definition.
- `src/routes/businessRoutes.js` — Business search (`GET /search`, registered before `/:id` so Express doesn't swallow it as an id param), public business profile, followers, connections, and posts-by-type lookups (`GET /:id`, `/:id/followers`, `/:id/connections`, `/:id/posts`), any logged-in role.
- `src/routes/postRoutes.js` — Post CRUD, business connections-feed, and shared like (`PUT /:id/like`) and comment (`GET`/`POST /:id/comments`) route definitions — like/comment are open to any logged-in role (2026-11-03: previously consumer-only), with the role branch handled inside the controllers.
- `src/routes/savedRoutes.js` — Consumer-only saved-posts route definitions (`GET /`, `POST`/`DELETE /:postId`).
- `src/routes/storyRoutes.js` — Authenticated stories route definition.
- `src/routes/collaborationRoutes.js` — Business collaboration route definitions, including participant-authorized completion.
- `src/routes/connectionRoutes.js` — Business connection request/status/accept-reject/disconnect route definitions.
- `src/routes/discoverRoutes.js` — Consumer discovery route definitions.
- `src/routes/notificationRoutes.js` — Consumer notification route definitions.
- `src/routes/followRoutes.js` — Consumer follow, unfollow, status, and following-list route definitions.

### Frontend

- `src/App.jsx` maps browser URLs to page components, protects signed-in routes and applies account-role restrictions. `src/account/` holds the session, signed-in profile and shared saved-post state.
- `src/pages/` contains the authentication, home, search, explore, notifications, profile, publishing, collaboration, saved and about screens. Search preserves its filters in the URL. Both roles can open `/businesses/:businessId`, and `/profile` opens the signed-in account.
- `src/components/` contains shared post cards, avatars, city selectors, countdowns, relationship buttons and dialogs. `src/lib/` contains API, image upload and date helpers.
- `src/layout/` provides the desktop sidebar and mobile navigation. `src/main.jsx` imports the component foundations, shared "Desi bazaar" light theme, business home styles and narrow-screen layouts. All theme colours and fonts are CSS variables on `:root` in `styles.css` (`--bg`, `--paper`, `--sunk`, `--line`, `--ink`, `--muted`, `--coral` (rani pink), `--gold` (marigold), `--blue` (peacock teal), their `-tint`/`-ink` pairs, `--print` block-print stripe, `--display` Rozha One, `--body` Inter); change the palette there rather than adding literal colours. All Desi bazaar dressing (toran garland, maroon cloth sidebar and phone tab bar, signboards, rangoli dividers, offer rings and paper tags, post stamps/arched photos/ticket countdowns/bead hashtags, ledger rails, shopfront shortcuts and Search results, kolam empty states, ledger-style form fields, round avatars) lives in `src/bazaar.css`, imported last in `main.jsx`; layout stays in the other stylesheets. The mobile More menu includes secondary destinations and logout.
- `vite.config.js` — Vite React configuration and `/api` proxy to `http://localhost:5000`.
- `vercel.json` (frontend) — Catch-all `rewrites` rule sending every path to `index.html`, required because the app uses `react-router`'s `BrowserRouter`; without it, refreshing on any non-root route (e.g. `/search`) 404'd on Vercel's static hosting instead of loading the SPA shell. Added 2026-11-21.
- `index.html` — Browser document shell and page metadata.
- `README.md` — Frontend product/UX brief covering audience roles, implemented flows, URL-based navigation, responsive requirements, integration boundaries, and local run instructions.

## Tech Stack

- Runtime: Node.js
- Backend: Express 4, CommonJS JavaScript
- Frontend: React, Vite, JSX
- UI icons: `lucide-react`
- Database: MongoDB, accessed through Mongoose 8
- Authentication: bcryptjs password hashing plus JWT Bearer tokens via `jsonwebtoken`
- Middleware/tools: CORS, dotenv, Nodemon, multer (multipart parsing)
- Image storage: Cloudinary (SDK `cloudinary`), configured via `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` in `backend/.env`; uploads go to `localyze/posts` or `localyze/profiles` folders.
- Frontend development proxy: Vite proxies `/api` to backend port 5000
- Database environment: Current `.env` is configured for MongoDB Atlas; the backend connection was verified successfully during this session.
- Backend testing: Jest + Supertest + `mongodb-memory-server` (added 2026-11-03 — no test framework existed before). `npm test` (from `backend/`) runs `backend/src/tests/*.test.js`; each suite spins up its own in-memory MongoDB instance (`src/tests/testDb.js`) rather than sharing process state across Jest workers. No frontend test framework yet.

## Known Issues / TODOs

- The backend has no `.env.example` in the current file inventory despite README setup instructions referring to it; `.env` exists and contains sensitive configuration that must not be committed.
- Root-level `atlas-credentials.env` and `credentials.txt` are sensitive-looking files that still exist locally — confirmed (2026-11-21) they are listed in root `.gitignore` and untracked by git (`git ls-files` shows neither), so the source-control exposure risk is resolved; rotating/removing the local files themselves is still up to the user.
- Frontend sessions are stored as JWTs in localStorage. The client checks token expiry when reading a session and fetches the current account profile, but does not refresh tokens; transient profile-fetch failures can leave the local session active until the API rejects it.
- Business post editing and deletion are available from the owner's profile; post performance/manage-stats screens are not implemented yet.
- Offer notifications target followers only; consumers who follow after an offer is published do not receive that historical notification.
- Stories show one latest non-expired post per followed/connected business; accounts with no relationships see an empty prompt rather than fake placeholder businesses.
- Legacy collaboration documents with `accepted` status are returned as `active`; new accepts persist as `active` and only participating businesses may mark them `completed`.
- About Localyze is an informational frontend page explaining how consumers, local businesses, and business collaborations form the ecosystem; it needs no backend endpoint.
- Sending a connection request or collaboration request only happens from a business's profile page — reachable now either by clicking their name on a post or via the new Search page's results, but there's no way to send a request directly from the search results list itself.
- The curated city list (`backend/src/constants/cities.js`) is India-only and fixed in code — adding a new city requires a code change/deploy, not an admin action. Businesses/consumers outside that list cannot register.
- `username` uniqueness is enforced per account type (a separate unique index on `User` and on `Business`), matching how `email` already behaves — a consumer and a business can currently register the same `@handle`. Decided to match the existing `email` convention rather than add a new cross-collection check; revisit if the product wants one global handle namespace.
- `backend/src/models/Activity.js` only logs consumer-initiated like/unlike and follow/unfollow actions — no "view"/impression tracking yet (there's no single-post-detail page in the frontend to trigger one from), and nothing reads the collection yet (no endpoint/UI) — it's groundwork for the future Explore page's ranking algorithm, not a feature in itself. `Activity.create()` calls are not wrapped in their own try/catch, so a write failure there would bubble up and fail the parent like/follow request too — consistent with how `Notification.insertMany` is handled elsewhere in this codebase, revisit if that coupling becomes a problem. As of 2026-11-03, business accounts can also like posts (`Post.businessLikes`) and comment, but `Activity` has no actor field to record a business's own engagement against (its `user` field is required and semantically consumer-only) — business likes/comments are not logged to `Activity` at all. If business engagement ever needs to feed the same future ranking signal, `Activity` needs an actor-type change, not just a new optional field.
- `backend/scripts/resetDatabase.js` is a manual dev-only utility (empties every collection via the configured `MONGO_URI`) — not wired into any npm script or CI step on purpose, since it's destructive and meant to be run deliberately by a human.
- The business search endpoint (`GET /api/businesses/search`) caps results at 30 with no pagination — fine at current scale, revisit if a city's business count grows past that.
- Cloudinary uploads have no server-side cleanup: if a user picks a photo/post image but never saves (abandons the edit form or the post-creation flow), the uploaded image stays in the Cloudinary account unreferenced by anything in the database.
- `POST /api/uploads/image` accepts an upload from any logged-in account with no per-endpoint rate limiting — fine for now, worth revisiting before any public deployment.
- Open business connection pairs are protected by a partial unique index on canonical `pairKey`; legacy rows without a key are still matched by participant IDs. Existing deployments must follow the documented pair-key migration before relying on the index for all records.
- Disconnecting from a business profile still uses the browser's native `window.confirm`; post deletion now uses the in-app `ConfirmDialog`.
- Deleted posts are kept forever (soft-delete, no retention/purge policy) — there is no admin/recovery UI to view or restore them, so they exist purely as an audit trail in the database.
- Cloudinary image deletion only happens for posts uploaded through the file-picker (`imagePublicId` set); older posts or ones with a hand-pasted `imageUrl` have no `imagePublicId` and their image (if any) is not cleaned up on delete — nothing to destroy without knowing the asset id.
- Editing or removing a post's image (`PUT /api/posts/:id` with a new or empty `imageUrl`/`imagePublicId`) does not destroy the previous Cloudinary asset — only full post deletion triggers cleanup.
- The business profile's stats row (followers/collaborations/connections counts) doesn't live-refresh after a connect/disconnect action on that same page — only the action button's own state updates immediately.
- Expired offers still drop out of the consumer discovery feed and the business connections feed once `expiresAt` passes (pre-existing feed-freshness filter, applies to all post types) — they only remain visible on the business's own profile Offers tab, which has no expiry filter. If offers should also stay visible (marked expired) in the scrolling feeds, that filter needs a postType-aware exception.
- `Countdown` re-renders on a 60-second interval, so it's accurate to the minute, not the second — fine for the "2d 8h" / "45m" granularity currently shown, but note if second-level precision is ever wanted.
- Backend has a Jest/Supertest/mongodb-memory-server suite (added 2026-11-03) covering offer-date enforcement, Explore, Saved, Comments, cross-role likes/comments, and selected connection/collaboration concurrency and legacy-pair cases; coverage elsewhere (auth, follows, uploads, business profile, etc.) remains limited. No frontend test suite exists.
- Saved posts remain consumer-only (not extended to businesses alongside likes/comments on 2026-11-03) — not asked for; revisit if business accounts should be able to bookmark posts too.
- The backend uses broad CORS configuration and should be restricted for production deployment.
- Git repository is active on branch `main` with remote `origin` configured as `https://github.com/ranjeetkalerk28-cell/localyze-review-1.git`; the latest verified checkpoint is commit `dd90504` (business likes/comments, pushed 2026-11-03).
- Deployment target is Vercel (both frontend and backend as separate Vercel projects) — the earlier `DEPLOYMENT_CHECKLIST.md` (Railway-specific) has been removed since it no longer matches the actual target and was actively misleading. Required Vercel project environment variables: frontend needs `VITE_API_BASE_URL` set to the deployed backend's URL + `/api` (Vite bakes this in at build time — changing it requires a redeploy, not just a dashboard edit); backend needs `CLIENT_URL` set to the deployed frontend's exact origin (no trailing slash) for the CORS allowlist in `app.js` to accept it. Neither value is verified as actually set in Vercel from this repo alone — confirm in each project's dashboard.
